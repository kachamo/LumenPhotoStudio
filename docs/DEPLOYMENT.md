# Lumen Photo Studio Deployment

How a built tree becomes something you can hand to someone else.

For compiler/Qt setup and per-platform build commands see
[`BUILDING.md`](BUILDING.md).

## Scope, honestly

What is real today:

- A correct `cmake --install` layout on Windows, macOS and Linux.
- macOS `.app` bundle metadata: bundle id, versions, copyright, Retina and
  dark-mode keys, and document-type associations for the image, RAW and Lumen
  file extensions.
- Linux desktop integration: `.desktop` entry, hicolor icon, AppStream
  metainfo.
- Windows `VERSIONINFO` resource on the `.exe`.

What is **not** done and is out of scope for now:

- No installers. There is no CPack configuration, no MSI/NSIS, no `.dmg`, no
  AppImage, no `.deb`/`.rpm`. Distribution is "staged directory + zip".
- No code signing and no notarization on any platform. macOS Gatekeeper will
  quarantine the bundle; Windows SmartScreen will warn.
- No application icon binaries. Only `resources/icons/lumen_logo_512.png`
  exists; the Windows `.ico` and macOS `.icns` still have to be generated by
  hand (see `BUILDING.md`). The build is wired to pick each of them up the
  moment it is committed, with no CMake change.
- No SBOM / dependency manifest for distro packaging. The AppStream metainfo
  declares `GPL-3.0-or-later`, matching the repository `LICENSE`; if that ever
  changes, `packaging/linux/studio.lumen.photostudio.metainfo.xml` has to be
  updated with it.
- No Qt translation/`.qm` deployment (the app is English-only).

## App metadata

| Field | Value |
|---|---|
| App name | Lumen Photo Studio |
| Version | 1.1.0 (`project(VERSION)` in `CMakeLists.txt`) |
| Organization name | Lumen |
| Organization domain | lumen.studio |
| CMake target | `LumenPhotoStudio` |
| Executable `OUTPUT_NAME` | `LumenPhotoStudio` on every platform |
| macOS bundle identifier | `studio.lumen.photostudio` |
| Linux desktop id | `studio.lumen.photostudio` |
| Icon source | `resources/icons/lumen_logo_512.png` |

The application version reported by `QCoreApplication::applicationVersion()`
comes from a generated header (`packaging/cmake/lps_build_info.h.in` ->
`<build>/generated/lps_build_info.h`), so it cannot drift away from
`project(VERSION)`.

## CMake install

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
cmake --install build --prefix dist/stage
```

On a multi-config generator add `--config Release` to both the build and the
install step.

Runtime data (plugin drop-in folder, preset drop-in folder, docs) is installed
under `LPS_INSTALL_DATA_DIR`, which is platform-dependent — see below. Qt
resources (icons, SVGs) are compiled into the executable through
`resources/resources.qrc` and are not installed separately.

### Known gap: the installed `plugins/` folder is not the one the app scans

`lps::PluginManager`'s default constructor resolves its directory as
`QCoreApplication::applicationDirPath() + "/plugins"`
(`src/plugins/PluginManager.cpp`), and `MainWindow` constructs it with no
argument. So at runtime the application looks next to the *executable*:

| Platform | Where the app looks | Where `cmake --install` puts it |
|---|---|---|
| Linux | `<prefix>/bin/plugins` | `<prefix>/share/LumenPhotoStudio/plugins` |
| Windows | `<prefix>/bin/plugins` | `<prefix>/share/LumenPhotoStudio/plugins` |
| macOS | `LumenPhotoStudio.app/Contents/MacOS/plugins` | `LumenPhotoStudio.app/Contents/Resources/plugins` |

These have never agreed on any platform; the installed folders are currently
staging placeholders only. `presets/` is in the same position — nothing
instantiates `lps::PresetManager` or calls `setPresetsDirectory()` yet.

Closing this needs a decision that is not a packaging change: either
`PluginManager` learns to resolve a platform-correct data directory (and on
macOS to walk up from `Contents/MacOS` to `Contents/Resources`), or the install
destination moves next to the executable. Until then, treat the installed
`plugins/` and `presets/` folders as layout reservations, not working drop-in
directories.

## Windows

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="C:/Qt/6.8.0/msvc2022_64"
cmake --build build
cmake --install build --prefix dist/windows
windeployqt --release dist/windows/bin/LumenPhotoStudio.exe
```

Resulting tree:

```
dist/windows/
  bin/
    LumenPhotoStudio.exe        <- plus everything windeployqt copies in
  share/
    LumenPhotoStudio/
      docs/
      plugins/
      presets/
```

Notes:

- `windeployqt` must come from the same Qt kit the app was built against.
- With a Visual Studio generator keep `--config Release` on both the build and
  the install command; the pre-install binary is at
  `build/bin/Release/LumenPhotoStudio.exe`.
- The `.exe` carries a `VERSIONINFO` resource generated from
  `packaging/windows/app.rc.in` (CompanyName, FileDescription, FileVersion,
  ProductName, LegalCopyright, OriginalFilename). Right-click > Properties >
  Details shows it.
- The `.exe` has **no** embedded icon until `packaging/windows/lumen.ico` is
  committed.
- If LibRaw was enabled, ship its DLL beside the executable. `windeployqt`
  only knows about Qt.
- Distribute by zipping `dist/windows`.

## macOS

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="$(brew --prefix qt@6)"
cmake --build build
cmake --install build --prefix dist/macos
macdeployqt dist/macos/LumenPhotoStudio.app
```

Resulting tree:

```
dist/macos/
  LumenPhotoStudio.app/
    Contents/
      Info.plist
      MacOS/
        LumenPhotoStudio
      Frameworks/               <- created by macdeployqt
      Resources/
        docs/
        plugins/
        presets/
```

### The bundle-relative data directory

This used to be wrong and is worth calling out. `LPS_INSTALL_DATA_DIR` was
`${CMAKE_INSTALL_DATADIR}/LumenPhotoStudio` on every platform, which on macOS
staged the plugin and preset folders into `dist/macos/share/...` — *outside*
the bundle. A `.app` is relocatable: the user drags it to `/Applications` and
the sibling `share/` tree is left behind, so the application could never reach
those folders at runtime.

`CMakeLists.txt` now switches the default on `APPLE`:

| Platform | `LPS_INSTALL_DATA_DIR` |
|---|---|
| macOS | `LumenPhotoStudio.app/Contents/Resources` |
| everything else | `${CMAKE_INSTALL_DATADIR}/LumenPhotoStudio` |

Both are relative to `CMAKE_INSTALL_PREFIX`, and the `install(DIRECTORY ...)`
rules for `plugins/`, `presets/` and `docs/` all follow it.

### Info.plist

Generated from `packaging/macos/Info.plist.in` via `configure_file` and wired
up with the `MACOSX_BUNDLE_INFO_PLIST` target property. It declares:

- `CFBundleIdentifier` = `studio.lumen.photostudio`
- `CFBundleName` / `CFBundleDisplayName` = `Lumen Photo Studio`
- `CFBundleVersion` / `CFBundleShortVersionString` = the project version
- `NSHighResolutionCapable` = true (Retina)
- `NSRequiresAquaSystemAppearance` = false (the app ships its own dark theme,
  so macOS must not force the legacy light appearance)
- `LSApplicationCategoryType` = `public.app-category.photography`
- `CFBundleDocumentTypes` for four groups: standard images
  (jpg/jpeg/png/tif/tiff/bmp/webp), camera RAW
  (cr2/cr3/nef/arw/dng/raf/orf/rw2), Lumen projects (lps/lpsproj) and Lumen
  presets (lxp/lpreset)

`CFBundleIconFile` is empty until `packaging/macos/LumenPhotoStudio.icns` is
committed.

## Linux

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
cmake --install build --prefix dist/linux
```

Resulting tree (`CMAKE_INSTALL_BINDIR` = `bin`, `CMAKE_INSTALL_DATADIR` =
`share`, from `GNUInstallDirs`):

```
dist/linux/
  bin/
    LumenPhotoStudio
  share/
    LumenPhotoStudio/
      docs/
      plugins/
      presets/
    applications/
      studio.lumen.photostudio.desktop
    icons/hicolor/512x512/apps/
      studio.lumen.photostudio.png
    metainfo/
      studio.lumen.photostudio.metainfo.xml
```

Everything under `applications/`, `icons/` and `metainfo/` is installed only
when `UNIX AND NOT APPLE`.

### Desktop entry

`packaging/linux/studio.lumen.photostudio.desktop` declares
`Categories=Graphics;Photography;RasterGraphics;`, `Exec=LumenPhotoStudio %F`
(so file managers can pass selections), `Icon=studio.lumen.photostudio` and a
`MimeType` list covering JPEG/PNG/TIFF/BMP/WebP plus the vendor RAW types
(`image/x-canon-cr2`, `image/x-canon-cr3`, `image/x-nikon-nef`,
`image/x-sony-arw`, `image/x-adobe-dng`, `image/x-fuji-raf`,
`image/x-olympus-orf`, `image/x-panasonic-rw2`).

`ui/main.cpp` calls `QGuiApplication::setDesktopFileName("studio.lumen.photostudio")`,
which is what lets Wayland compositors associate the running window with this
entry and therefore show the right icon in the dock.

`StartupWMClass=LumenPhotoStudio` is the X11 fallback for the same job. It is
a best-effort value: Qt derives `WM_CLASS` from the executable name and the
application name, so if the icon is still wrong under X11, check the real
value with `xprop WM_CLASS` on a running window and update the key.

The `.lps` / `.lxp` extensions are **not** registered as Linux MIME types. That
needs a `shared-mime-info` XML package which has not been written.

### For a real system install

The desktop and icon caches must be refreshed. A distro package would do this
in its post-install hook:

```
update-desktop-database /usr/share/applications
gtk-update-icon-cache -f -t /usr/share/icons/hicolor
```

### Verifying the metadata

```
desktop-file-validate dist/linux/share/applications/studio.lumen.photostudio.desktop
appstreamcli validate dist/linux/share/metainfo/studio.lumen.photostudio.metainfo.xml
```

`appstreamcli --strict` will also ask for a `<releases>` block and screenshots;
neither is present yet.

### Portable bundles

AppImage and Flatpak are both viable and neither is set up. AppImage would want
`linuxdeploy` with the `qt` plugin pointed at `dist/linux`; Flatpak would want
a manifest built on `org.kde.Platform`, reusing the `.desktop` and metainfo
files this build already installs.

## Post-deploy verification

The binary self-checks without a display:

```
QT_QPA_PLATFORM=offscreen dist/linux/bin/LumenPhotoStudio --smoke-test
echo $?
```

Exit code 0 means `MainWindow` constructed, showed and pumped the event loop
successfully. Exit code 1 means an exception escaped startup. This is the check
CI runs; it is also the fastest way to confirm a deployed tree has every Qt
plugin it needs, because a missing platform plugin aborts the process.

On Windows the executable is built with `WIN32_EXECUTABLE ON` and has no
console, so check `$LASTEXITCODE` rather than looking for output.
